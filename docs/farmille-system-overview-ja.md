# Farmille システム全体ガイド（非エンジニア向け）

**この資料について**
Farmille がどんな仕組みで動いているか、技術・セキュリティ・稼働状況を、専門用語を避けつつ「実際に使っている名前」も交えて説明する読み物です。1時間程度の説明用に、上から順に読めば全体像がつかめる構成にしています。各章は独立しているので、気になる章だけ拾い読みもできます。

> ひとことで言うと：**「農家さんが BS資材（微生物・生物農業資材）のリアルな使用レビューを共有・閲覧でき、メーカーが自社資材を載せられる、Webのレビュープラットフォーム」** です。

---

## 1. まず全体像 ― レストランに例えると

Webサービスは「3つの役割」に分かれています。レストランで例えると分かりやすいです。

```
   お客さま（農家・メーカー・運営者）
            │  ブラウザ／スマホで操作
            ▼
 ┌─────────────────────────┐
 │  ① ホール（画面）          │  ← 見た目・操作。Next.js / Vercel
 │     "フロントエンド"        │
 └─────────────┬───────────┘
            │  「これ持ってきて」と注文
            ▼
 ┌─────────────────────────┐
 │  ② 厨房（頭脳）            │  ← ルール判定・計算。FastAPI / Google Cloud
 │     "バックエンド / API"    │
 └─────────────┬───────────┘
            │  食材の出し入れ
            ▼
 ┌─────────────────────────┐
 │  ③ 倉庫（保管庫）          │  ← データ・写真・会員情報。Supabase
 │     "データベース"          │
 └─────────────────────────┘
```

- **① ホール（フロントエンド）**＝お客さまが見て触る画面。
- **② 厨房（バックエンド）**＝「この人にこの操作をさせてよいか」を判断し、データを取り出して整える頭脳。
- **③ 倉庫（データベース）**＝製品・レビュー・会員・写真などを安全に保管する場所。

**重要な原則**：お客さま（ホール）は**倉庫に直接入れません。** 必ず厨房（バックエンド）を通します。これが後述するセキュリティの土台です。

## 2. 使っている技術（実名つき）

「何を使っているか」を正直に出します。いずれも世界的に広く使われている定番のサービス・道具です。

| 役割 | 使っているもの（実名） | ひとことで言うと | 例えるなら |
|---|---|---|---|
| ① 画面（フロント） | **Next.js / React / TypeScript / Tailwind CSS** | Webサイトの見た目と操作を作る定番の道具 | レストランのホール内装・接客 |
| ① の公開先 | **Vercel** | 画面を世界中に高速配信するクラウド | ホールが建っている一等地 |
| ② 頭脳（API） | **FastAPI / Python** | ルール判定とデータ処理を行うプログラム | 厨房のシェフ |
| ② の動作場所 | **Google Cloud Run（Googleのクラウド）** | アクセス量に応じて自動で増減するサーバー基盤 | 必要なだけ厨房を増やせる仕組み |
| ③ 倉庫（DB＋認証＋写真） | **Supabase（中身は PostgreSQL）** | データ保管・ログイン認証・画像保管を一手に担うサービス | 鍵付きの倉庫＋受付＋写真庫 |
| 秘密情報の保管 | **Google Secret Manager** | パスワードや鍵を安全に保管する金庫 | 厨房の金庫 |

**なぜこの構成か（非エンジニア向けの要点）**
- どれも「自前で全部作る」のではなく、**信頼できる既製サービスに任せられる部分は任せる**ことで、少人数でも安全・高速に運営できます。
- 使った分だけ課金される仕組み（Cloud Run / Vercel）なので、**アクセスが少ない時はほぼ無料、増えたら自動で拡張**します。

## 3. ユーザーがボタンを押すと何が起きるか（データの流れ）

例：農家さんが「レビューを投稿」ボタンを押したとき。

```
[農家のスマホ]
   │ ①「このレビューを保存して」
   ▼
[① 画面 (Next.js / Vercel)]
   │ ② ログイン情報(身分証)を添えて厨房へ依頼
   ▼
[② 頭脳 (FastAPI / Google Cloud)]
   │ ③ 「この人は農家か？ 投稿してよい人か？」を確認（第一の関所）
   │ ④ OKなら "承認待ち" としてデータを保存指示
   ▼
[③ 倉庫 (Supabase)]
   │ ⑤ さらにDB側でも権限を再確認（第二の関所）→ 保存
   ▼
   結果が逆向きに返り、画面に「投稿しました（承認後に公開）」と表示
```

ポイントは、**画面 → 頭脳 → 倉庫** と必ず一方向に通し、**関所（権限チェック）を二重に置いている**こと。次のセキュリティ章につながります。

## 4. サイトの構成（画面マップ）

Farmille は大きく **4つの利用面** に分かれています。

```
Farmille
├─ 公開サイト（ログイン不要でも閲覧可）
│   ├─ 資材一覧 / 資材詳細（レビュー・出典リンク付き）
│   ├─ 製造元（メーカー）一覧
│   └─ お知らせ・記事
│
├─ 会員ページ（ログイン後）
│   ├─ レビュー投稿・自分のレビュー
│   ├─ お気に入り（マイ資材）
│   └─ アカウント設定（メール確認・パスワード変更）
│
├─ メーカー向け（メーカー会員）
│   ├─ 自社プロフィール
│   └─ 自社資材の登録・編集（運営の承認後に公開）
│
└─ 運営（管理者）ダッシュボード ※2要素認証必須
    ├─ メーカー承認 / 資材マスタ管理 / ユーザー管理
    ├─ レビュー承認（投稿を公開前にチェック）
    └─ 通報管理 / 記事管理 など
```

## 5. 利用者の種類（ロール）と「できること」

人によって**できる操作が変わる**仕組みです。

| 種類（ロール） | 主にできること |
|---|---|
| **農家 (farmer)** | レビュー投稿・写真アップロード・お気に入り |
| **JA普及員 (ja_staff)** | レビュー投稿（将来 JA 向け機能を予定） |
| **研究者 (researcher)** | レビュー投稿（学術的な視点） |
| **メーカー (maker)** | 自社資材の登録・管理 |
| **運営 (admin)** | 全体の承認・管理（2要素認証が必須） |
| 未設定 (unassigned) | 登録直後の状態（オンボーディングで種類を選ぶ） |

> 「誰が何をしてよいか」をシステムが常に判断するので、たとえばメーカーが他社の資材を勝手に編集する、といったことは起きません。

## 6. 主な機能（いま動いていること）

- **資材データベース（約 379 製品が公開中）**：BS資材を検索・比較でき、効果タグ・対象作物・主成分などで整理。
- **レビュー（承認制）**：農家・研究者などが現場の使用感を投稿。**投稿は即公開ではなく、運営が確認・承認してから公開**（品質と表現の適正化のため）。
- **出典リンク**：製品情報には「どこの情報か」が分かる公式出典へのリンクを表示し、信頼性を担保。
- **メーカーによる資材登録**：メーカーが自社資材を登録 →**運営が承認 → 公開**。承認前でも、登録した本人は自分の資材ページを確認できます。
- **マイページ／アカウント設定**：メール確認・パスワード変更などを全会員が利用可能。
- **運営ダッシュボード**：保留中メーカー・承認待ちレビューなどの件数をひと目で把握し、各管理画面へ移動。

## 7. セキュリティ ― どう守っているか（重要）

「農家さんの個人情報やレビュー、メーカーの資材情報を、どう安全に扱っているか」。Farmille は**多層防御**（一つ破られても次がある）で設計しています。

1. **二重の関所（BFF＋RLS）**
   画面（フロント）は**データベースに直接触れません。** 必ず頭脳（バックエンド）を経由し、
   - **第一の関所**：バックエンド（FastAPI）が「この人にこの操作の権限があるか」を判定。
   - **第二の関所**：データベース（Supabase の RLS＝行レベルセキュリティ）が、念のためもう一度チェック。
   万一どちらかに穴があっても、もう一方が守ります。

2. **ログイン認証（Supabase Auth）**
   会員のログインは Supabase の認証基盤が担当。本人確認には**JWT（改ざん検知できる電子的な身分証）**を使い、毎リクエストで検証します。

3. **運営アカウントは2要素認証（2FA）必須**
   管理画面に入れる運営者は、パスワードに加えて**認証アプリのワンタイムコード**が必須（ADR-0012）。万一パスワードが漏れても管理画面は守られます。

4. **秘密情報はコードに書かない**
   データベースの鍵などの機密は **Google Secret Manager（金庫）** に保管し、プログラム実行時だけ読み出します。**画面側（ブラウザ）には機密の鍵を一切渡しません。**

5. **通信はすべて暗号化（HTTPS）**
   ブラウザ ⇄ サーバー間の通信は暗号化され、途中で盗み見されません。

6. **入力の検証と、レビューの事前審査**
   送られてきたデータは形式・内容を検証。レビューは**公開前に運営が審査**するため、不適切な投稿がそのまま世に出ることを防ぎます。

7. **環境の分離と最小権限**
   開発用と本番用でデータベースを**完全に分け**、本番には必要最小限の権限しか与えない運用にしています（ADR-0016）。

8. **継続的な脆弱性チェック**
   使っている部品（ライブラリ）に既知の弱点がないか定期的に点検（pnpm audit / pip-audit）。
   *例：* 直近でもログイン後の遷移に関する脆弱性（外部サイトへ誘導されうる「オープンリダイレクト」）を**発見してその場で修正**しました。問題を見つけたら塞ぐ、を継続しています。

## 8. いまの稼働状況（本番システム）

- **公開中**：本番サイトはすでに稼働しています。
  - 画面：**Vercel**（本番）
  - 頭脳：**Google Cloud Run**（本番、`farmille-api`）
  - 倉庫：**Supabase**（本番プロジェクト）
- **データ規模**：公開資材 **約379点**、複数の製造元、現場レビューが集まり始めている段階。
- **運用の特徴**：
  - コードを更新（マージ）すると**自動で本番に反映**される仕組み（Vercel）。
  - サーバー（Cloud Run）は**アクセスに応じて自動で増減**。普段は最小、混雑時に拡張。
  - **安全なデプロイ順序**を徹底（例：データベースの構造変更を先に適用してからプログラムを更新する、など）。順序を守ることで「更新した瞬間に画面が真っ白」を防いでいます。

## 9. 開発の進め方（品質をどう担保しているか）

- **変更は必ず記録に残す**：すべての修正は履歴（Git）として残り、いつ・誰が・何を変えたか追跡可能。問題があれば**すぐ元に戻せます**。
- **レビューしてから反映**：変更は一度「提案（プルリクエスト）」にまとめ、内容を確認してから本体へ取り込みます。
- **自動テスト**：画面・頭脳それぞれに自動チェック（型チェック・テスト）があり、おかしな変更が混ざらないようにしています。
- **重要な決定は文書化（ADR）**：「なぜこの技術・この方針にしたか」を意思決定記録として残し、後から判断の理由をたどれます（例：ADR-0013 でクラウドを Google Cloud に決定）。

### まとめ（説明の締めに）
Farmille は、**定番で信頼できる技術（Next.js / Vercel / FastAPI / Google Cloud / Supabase）**を組み合わせ、**画面・頭脳・倉庫を分離**し、**二重の関所と2要素認証で守りながら**、すでに**本番で稼働**しています。少人数でも、安全性・拡張性・更新の速さを両立できる構成です。
