# Farmille v1 機能要件ドキュメント（農家向け 6 画面スコープ）

## 0. このドキュメントについて

### 0.1 目的と読者

本書は Farmille v1 の**機能要件**を、PRD（戦略レイヤー）と spec（実装契約レイヤー）の中間粒度（L3）でまとめるものです。

- **PRD**（`docs/requirements/farmille-prd.md`）: ミッション・ターゲット・KPI・ロードマップなど「なぜ・誰のために」を扱う
- **本書**: 「v1 で何を作るか」を **農家さん向け 6 画面**を中核として、ユーザーストーリー / 画面要素 / 主要データ項目 / ロール権限 / スコープ外 / 残課題 まで定義する

読者は共同創業者 3 名と worker / evaluator セッションです。

## 1. プロダクトコンセプト（v1）

### 1.1 v1 のポジショニング: AgList + Carview MyCar 参照モデル

2026-04-29 会議で v1 は「カービュー × アグリスト」中間モデルとして定義された。本書では参照プラットフォームをさらに具体化し、**AgList（製品 / 企業 / 記事の 5 軸ハブ構造）+ Carview MyCar（マイ資材の保管 + 候補併存）**を 6 画面の参考形とする（ホーム画面の UI 構成はアイハーブを参照）。

| 参考プラットフォーム | Farmille v1 が踏襲する点 | Farmille で補完する欠落（差別化） |
|---|---|---|
| **AgList**（agriculture review） | 「製品 / 企業 / 記事 / 販売店 / 推薦」5 軸ハブ構造 / フィルタ（location / crop / feature）/ メーカー自記の企業ページ / leaderboard 別建て | お悩み相談室、「使用版」CTA、否定的レビュー（★1-5）、編集体制透明化された記事 |
| **Carview MyCar** | 最大 10 台保管 / 「所有」+「欲しいクルマ（候補）」の両方を保管 / 1 台あたり管理項目（車検・保険・オイル交換）/ 通知（車検・保険更新・適合パーツ） | （MyCar 単体にプロフ UI なし → みんカラ参考で農家プロフ画面を補完） |
| **みんカラ**（Carview 系コミュニティ） | ユーザーページのリッチ実装（プロフィール表示・自身の投稿一覧） | – |
| カービュー（車情報サイト） | 専門家レビュー・ユーザーレビュー・関連製品表示 | – |
| アグリスト（農業 SNS、AgList 表記揺れ） | メールベース問い合わせ（「使用版に興味がありますか？」型 CTA） | – |
| 食べログ | レビュー 200 件以上で星評価導入 / ユーザー信頼度で重み付け（v1 は星評価ありでも自動ランキングなし） | – |
| **アイハーブ** | ホーム画面 UI 構成（検索バー / 広告 / 注目商品 / 記事一覧） | – |

v1 は「コミュニティ・AI・自動ランキング」を持たない**レビュー / カタログ / 企業情報 / マイ資材 / 農家プロフ**を中心とする。

### 1.2 v1 ターゲットと提供価値

PRD §1.2 / §1.3 を継承。**v1 中心は farmer**。JA 普及員 / 研究者は v1 では農家と同等ビューを共有する読み手 + 投稿者として振る舞う（専用ビューは未確定、§5.3）。

| ロール | v1 の核体験 |
|--------|------------|
| 農家（farmer） | 6 画面全体が想定 UX。圃場条件に近い実例レビューを横断検索 / マイ資材で気になる資材を保管 / メーカーから「使用版」オファーを受け取る |
| JA 普及員（ja_staff） | 農家と同等ビュー。組合員提案エビデンスとしてレビュー閲覧、普及員視点でのレビュー投稿 |
| 研究者（researcher） | 農家と同等ビュー。現場データへのアクセス、専門的視点でのレビュー投稿 |
| メーカー（maker） | 自社資材登録（既存 `/maker/products`）・メーカー公開ページ運用（§3.3 連動）/ お悩み相談室応答（業務フロー未確定） |

### 1.3 「中立的情報インフラ」のポジション

PRD §9.3 を継承。v1 段階から以下を維持する。

- 農家側の体験は無料・広告なし（自社記事・月次レポートは掲載するが、メーカー有償広告枠は v1.5+、アフィリエイト広告は v1〜v3 不採用）
- メーカー課金の入り口を v1 では作らない（B2B LP は §4 v1 アウト、再検討は §5.4）
- 自社製品販売は行わない

## 2. ロール定義

### 2.1 ロール一覧と v1 での扱い

PRD §3 を継承。

| ロール | 内部キー | 登録方法 | v1 の核機能 | v1 専用ビュー |
|--------|----------|---------|------------|--------------|
| 農家 | `farmer` | サインアップで自己選択 | 6 画面の主役 / レビュー投稿 / マイ資材 / 検索 | 6 画面全体 |
| JA 普及員 | `ja_staff` | 管理者割当（v1 はサインアップ不可） | 農家と同等のレビュー権限 | なし（農家ビュー共有） |
| 研究者 | `researcher` | 管理者割当（v1 はサインアップ不可） | 農家と同等のレビュー権限 | なし（農家ビュー共有） |
| メーカー | `maker` | サインアップで自己選択（v1 は承認なし、§5.3） | 自社資材登録 / メーカー公開ページ運用 / お悩み相談室応答 | `/maker/products` のみ（拡張ダッシュボードは未確定 §5.3） |
| 未確定 | `unassigned` | サインアップ直後 | プロフィール設定のみ | – |
| 未ログイン | （なし） | – | 製品 / メーカー / 注目の資材 / 記事 / 企業 の閲覧 | – |

> **重要**: v1 では JA 普及員 / 研究者の専用ビュー、メーカーダッシュボードの拡張、サインアップ後のロール別ビュー分岐ルールは**未確定**（§5.3）。実装提案も着手もしない。

### 2.2 二層構造（実装観点）

ロールは Supabase Auth の `app_metadata.role`（JWT 由来、改ざん不可）と `public.users.role`（DB 列、SQL 集計用）の両方に保持する。書き込みは必ず `POST /v1/auth/register-role` 経由で原子的に両方更新する。

詳細は `docs/decisions/0002-reviews-insert-role-scope.md` 参照。

## 3. v1 で「やる」: 農家さん向け 6 画面（L3 詳細）

> 本章が v1 機能要件の中核。各画面で L3 8 サブセクションを完備する。

### 3.1 ホーム画面 🟡

#### 3.1.1 機能サマリ
未ログイン向けランディングとログイン済 `/home` の双方で、検索バー上部・自社記事広告枠・注目の資材（手動キュレーション）・記事一覧（月次〜週次レポート）を AgList の 5 軸ハブ構造とアイハーブの UI 構成を組み合わせて提供する。

#### 3.1.2 ユーザーとゴール
- 未ログイン訪問者: 検索バーから興味ある資材へ直行する / 「Farmille は何のサイトか」を即理解する / SEO 流入の入口
- 農家（ログイン済）: 注目の資材と最新記事を眺めて、知らなかった資材に出会う
- メーカー: 自社記事・自社資材が露出する場として認識する

#### 3.1.3 ユーザーストーリー
- 未ログインの農家として、トップページの検索バーに作目名や悩みを入れて、関連資材一覧に飛びたい。最初に知りたいのは「どの資材があるか」だから。
- 農家として、ホームに並ぶ「注目の資材」を眺めて、自分の作目で使えそうな新規資材を見つけたい。検索クエリを思いつかない時の入口にしたい。
- 農家として、月次〜週次レポート記事を読んで、業界トレンドや BS 資材の使い方の知見を得たい。
- メーカーとして、自社製品が「注目の資材」に手動掲載されることを期待する。

#### 3.1.4 画面要素
- `/`（未ログイン）と `/home`（ログイン済）で同じ構造。出し分けはヘッダーのログインボタン / アバターのみ
- **上部**: 検索バー（カタログ §3.2 への入口）+ メインビジュアル
- **広告 / 自社記事エリア**: 1〜3 枠。初期は自社記事・キャンペーン告知。将来的にメーカー広告枠化（v1 は自社のみ、メーカー有償広告枠は v1.5+）
- **「注目の資材」セクション**: 横並び 4-8 製品（AgList の leaderboard を参考にしつつ、**手動キュレーション**で運営が選定。自動ランキングではない）
- **「月次〜週次レポート / 記事」一覧**: 直近 3-6 件。タイトル・サムネイル・公開日
- **フッター**: 静的ページ（利用規約 / プライバシーポリシー / お問い合わせ / About）への導線

#### 3.1.5 主要データ項目
- `featured_products`（**所有節は本節**、新規）: 運営手動投入の「注目の資材」キュレーション用テーブル。カラム構成は spec 起草時 DOA レビューで確定（運営手動運用を前提に最小カラム設計）
- `articles` — 記事の参照元（**正は §3.4.5**、本節は読み取り参照のみ）
- `home_banners`（**所有節は本節**、新規）: 自社記事 / キャンペーン告知用。カラム構成は spec 起草時 DOA レビューで確定

#### 3.1.6 ロール権限
- 閲覧: 全ユーザー（未ログイン含む）
- 編集: 運営（v1 は SQL 直アクセス、管理画面は v1 アウト）

#### 3.1.7 v1 スコープ外
- メーカー有償広告枠購入 UI（v1.5+）
- パーソナライズドレコメンド（行動履歴ベース、SKILL §1.4 やらない）
- 「注目の資材」の自動選定ロジック（SKILL §1.4 やらない、手動キュレーションで代替）
- アフィリエイト広告（v1〜v3 不採用）

#### 3.1.8 残課題
§5.2.7 / §5.2.6 / §5.2.14 を参照。

### 3.2 製品（一覧 + 詳細）✅+🔥

#### 3.2.1 機能サマリ
BS 資材を中心とした製品カタログ。フィルタ付き検索の一覧と、★1-5 レビュー（本文 + 写真）・関連資材・「使用版」CTA を含む詳細ページから成る。AgList の製品ページを参考とし、AgList にない**否定的レビューも書ける**点で差別化する。

#### 3.2.2 ユーザーとゴール
- 農家: 作目・効果・成分でフィルタして候補を絞る / 詳細ページのレビューで業務判断する / 「使用版」CTA でメーカーから案内を受け取る
- JA 普及員: 組合員に推奨する前にレビュー確認のエビデンスを取る
- 研究者: 特定成分・効果の資材を横断的に調べる
- 未ログイン: SEO 経由で詳細に到達 → サインアップ動機につなげる

#### 3.2.3 ユーザーストーリー
- 農家として、作目「イチゴ」と効果「収量増加」でフィルタした一覧から、レビュー件数の多い資材を選んで詳細を読みたい。
- 農家として、製品詳細ページで★評価分布と本文 1-2000 字のレビュー（写真付き）を読んで、自分の圃場に応用できるか判断したい。
- 農家として、製品詳細ページの「関連資材」から類似製品に遷移したい。比較検討しているから。
- 農家として、興味ある資材の「使用版にご興味がありますか？」CTA を押して、メーカーから直接案内を受けたい。
- メーカーとして、自社製品の詳細ページが正しく表示されることを確認したい。

#### 3.2.4 画面要素
- **一覧**: `/products`（本リポ実装）/ `/bs-materials`（MVP） — **URL 命名は §5.2 で要決定**
  - フィルタ: タイプ（BS資材 / 農薬 / 肥料 / 土壌改良材）、作目カスケード（大 6 / 中 27 / 個別 547）、BS 製品分類（8 種）、BS 主たる効果・効能（約 20 項目）
  - 表示: 製品カード（画像 / 製品名 / メーカー名 / ★評価 / レビュー件数 / 効果タグ）
- **詳細**: `/products/[id]` / `/bs-materials/[id]`
  - 上部: 製品名・メーカー名（リンク先 §3.3）・画像・含有成分タグ・効果タグ・概要
  - レビュー: ★評価分布（1-5）/ レビュー一覧（本文 1-2000 字 + 写真最大 3 枚）/ レビュー投稿ボタン（要ログイン）
  - 関連資材: **同 BS 分類 + 同主要効果**ベース（行動履歴ベースは v1 アウト）
  - メーカーの「この製品の使用版にご興味がありますか？」CTA（§3.3 と連動）

#### 3.2.5 主要データ項目
既存 `products` / `reviews` / `manufacturers` / `crops` / `product_crops` / `product_categories` / `product_effects` テーブルを活用。新規追加なしで実現可能。

関連資材は v1 では「同 BS 分類 + 同主要効果」での絞り込みクエリで実現する（埋め込み・行動ベースは v2-v3）。

「使用版」CTA は §3.3.5 の `sample_requests` テーブルを起点とする（所有節は §3.3）。

#### 3.2.6 ロール権限
- 閲覧: 全ユーザー
- レビュー投稿動線（要ログイン）: farmer / ja_staff / researcher（投稿仕様は既存 spec `review-post.md`）
- 「使用版」CTA 押下: farmer / ja_staff / researcher（要ログイン）
- 編集: メーカーは自社製品のみ（既存 spec `maker-product.md`）

#### 3.2.7 v1 スコープ外
- 行動履歴ベースの関連資材レコメンド（v2-v3）
- 自然言語検索（v2 以降、AI 機能と一体）
- 比較ビュー（複数製品を横並び比較）
- AgList のような **推薦のみモデル**（Farmille は★1-5 + 否定レビュー可で差別化）

#### 3.2.8 残課題
§5.2.8 / §5.2.15 / §5.2.3 を参照。

### 3.3 企業（メーカー公開）ページ 🟡

#### 3.3.1 機能サマリ
メーカーごとに公開される「企業情報 + 自社製品一覧 + **お悩み相談室**（スレッド形式）+ **「使用版」案内 CTA**」のページ。AgList の企業ページが参考形だが、お悩み相談室と「使用版」CTA は **AgList にない Farmille 独自の差別化要素**として明示的に強調する。

#### 3.3.2 ユーザーとゴール
- 農家: 興味ある資材のメーカー背景を理解する / お悩み相談室で疑問を投げる / 使用版案内に興味があれば手を挙げる
- JA 普及員: メーカーの信頼性・対応姿勢を確認する
- メーカー: 自社の発信チャネルとして運用する / 農家の疑問にスレッドで応答する / 「使用版」案内で農家リードを獲得する

#### 3.3.3 ユーザーストーリー
- 農家として、製品詳細から企業ページに飛んで、メーカーの「強み・特徴」「提供価値」「本社所在地」を読みたい。資材選定に背景情報が要るから。
- 農家として、お悩み相談室にスレッドを立てて「夏場の高温時の使い方」を質問したい。レビュー単位の議論では収まらない疑問だから。
- 農家として、製品詳細または企業ページの「この製品の使用版にご興味がありますか？」ボタンを押して、メーカーから直接案内を受けたい（メールベース）。
- メーカーとして、お悩み相談室の自社スレッドに返信したい。農家との対話で信頼を築きたいから。
- メーカーとして、使用版案内に手を挙げた農家のメールアドレスを受け取って、直接コンタクトしたい。

#### 3.3.4 画面要素

### 3.5 マイ資材 🟡

#### 3.5.2 ユーザーとゴール

## 4. v1 で「やらない」（恒久 or 長期）

> SKILL §1.4 の「やらない」リストと完全整合。同一情報の重複を避けるため、SKILL.md §1.4 へリンクし、本節は要点のみ表で列挙する。

### 4.1 機能として v1 アウト

詳細・検討再開の条件は SKILL §1.4 参照。

| 項目 | v1 アウトの理由（要約） |
|------|----------------------|
| AI によるレビュー構造化・自然文検索・要約 | データ不足（2,000-3,000 件以上のレビュー蓄積待ち） |
| コミュニティ機能 `/community`（フォーラム / グループ） | 業務フロー大物、需要未検証 |
| 自動ランキング（★評価・レビュー数集計）、`/ranking` `/leaderboard` | 公平性懸念、月次〜週次レポート手動公開で代替（§3.4） |
| マッチング機能（サンプル取引・購買仲介） | 業務フロー設計重い、メールベース「使用版」CTA で代替（§3.3） |
| DM 機能（メーカー↔農家の一対一通信） | 法規制（特商法・電気通信事業法） |
| 音声入力レビュー | 専門用語認識精度・コスト |
| モバイルアプリ（iOS / Android） | リソース、PWA で代替検討 |
| プッシュ通知・リアルタイム更新 | 流入確保が先 |
| 管理者画面 | SQL 直アクセスで代替 |
| インセンティブ設計（割引・ランク・バッジ） | ピュア価値検証優先 |
| 農協正式連携（JA 別ダッシュボード） | パイロット選定待ち |
| Google 以外の OAuth（v2 含む） | ターゲット層が Google 中心 |
| PWA 化（v2 含む） | モバイル流入増加待ち |
| イベント機能（メーカー主催勉強会・千人規模通知） | メーカーリレーション構築が先 |
| 行動履歴ベースのレコメンド | データ量・計算基盤コスト |
| B2B ランディング `/b2b/*` | 課金モデル / メーカー有料化方針未確定 |
| カテゴリ・作目独立ページ `/categories` `/crops` | `/products` のフィルタで吸収可能 |

### 4.2 アーキテクチャ原則上の不採用

設計判断辞書（`.claude/skills/farmille-architecture-principles/SKILL.md`）に基づく**恒久的不採用**。

| 項目 | 理由 |
|------|------|
| Supabase Edge Functions | ポータビリティ予算（ベンダーロックイン回避） |
| Next.js API Routes でのバックエンド | 責務分離原則（ビジネスロジックは FastAPI 集約） |
| ORM（Prisma / Drizzle） | DOA 優先（SQL 直叙述で DB 設計を不可逆として扱う） |
| フロント → Supabase 直接 DB アクセス | 責務分離原則（例外は `supabase.auth.*` と `supabase.storage.*` のみ） |
| `RAILWAY_*` 等のプラットフォーム固有環境変数の直接参照 | ポータビリティ予算 |
| `user_metadata` への role 書き込み | ロール改ざん防止（真実値は `app_metadata.role` と `public.users.role`） |

## 6. アーキテクチャ準拠（要点）

設計判断辞書（`.claude/skills/farmille-architecture-principles/SKILL.md`）の要点のみ抜粋。本書の機能要件はすべて以下の原則に従って実装される。

| 原則 | v1 機能要件への含意 |
|------|---------------------|
| DOA 優先（DB は不可逆、UI は可逆） | §3 各節の「主要データ項目」は spec 起草時に DOA レビューを経て確定。jsonb 濫用を避け、運営手動運用を許容して最小スキーマで開始 |
| ポータビリティ予算 | Supabase Edge Functions / `RAILWAY_*` 直参照を本要件のいずれの機能でも採用しない |
| 責務分離（BFF 集約） | §3.3「使用版」案内 / §3.5 マイ資材通知含め、すべて FastAPI `/v1/*` 経由。フロントは `supabase.auth.*` / `supabase.storage.*` の 2 例外以外で Supabase を叩かない |
| 二重防御（FastAPI 第一防御 + RLS 第二防御） | §3.3 メーカー編集権限 / §3.5 本人限定 / §3.6 本人限定 / §3.4 運営限定 はすべて両層で実装 |
| v1 スコープ厳守（3 区分） | §4「やらない」を実装中に動かさない。§5「未確定」を勝手に「やる」へ昇格させない。AI / コミュニティ / 自動ランキング を「ついで実装」しない |

詳細・判断例・アンチパターンは `.claude/skills/farmille-architecture-principles/SKILL.md` を参照。

### 7.1 AgList の弱点（Farmille 差別化余地のサマリ）

researcher 調査より:
- **お悩み相談室なし** → §3.3 で実装（AgList にない要素として強調）
- **試用 CTA なし** → §3.3 で「使用版に興味がありますか？」CTA を実装
- **否定的レビューが書けない**（推薦のみモデル） → §3.2 で★1-5 + 本文 1-2000 字の正直なレビュー
- **編集体制が不透明な記事** → §3.4 で運営手動キュレーション + 著者明示

### 7.2 Carview MyCar の踏襲ポイント（マイ資材設計の核）

- **「所有しているクルマ」+「欲しいクルマ（候補）」の両方を保管** → §3.5 で「お気に入り」+「候補」併存タブ設計
- **最大 10 台保管** → §3.5.5 のお気に入り上限件数は §5.2 で要決定
- **メーカー / ディーラーから個別ユーザーへの直接通知チャネルなし（運営仲介型）** → §3.3.7 §3.5.7 の DM 不採用と整合
