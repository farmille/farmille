## 1. プロダクト概要

### 1.1 ミッション

**BS資材（生物・微生物農業資材）の現場使用感を、現場の言葉で集めて構造化する。**

農薬・化成肥料の代替として注目される BS 資材は、効果の出方が圃場・作目・気候で大きく変わるため、メーカー公表のスペックだけでは導入判断が難しい。Farmille は実使用者（農家・JA 普及員・研究者）のレビューを集積し、メーカー・購入検討者の双方が**業務判断に使えるレビュープラットフォーム**を目指す。

### 1.2 ターゲットユーザー

| セグメント | 役割 | Farmille での行動 |
|---|---|---|
| 農家 | BS 資材の購入検討 / 利用者 | 資材検索、レビュー閲覧、レビュー投稿、AI 検索、コミュニティ閲覧 |
| JA 普及員 | 組合員への資材推奨 | レビュー閲覧、現場知見の投稿、コミュニティ参加（v2 で JA ダッシュボード） |
| 研究者（大学・農研機構等） | 資材効果の学術的検証 | レビュー閲覧、専門的視点での投稿 |
| メーカー | 自社資材の認知獲得・市場フィードバック | 自社資材登録、メーカー公開プロフィール編集（v2 で分析機能） |

### 1.3 提供価値（4 ロール × 2 軸）

| ロール | 「探す」価値 | 「貢献する」価値 |
|---|---|---|
| 農家 | 圃場条件に近い実例レビューを横断検索、AI による意味検索、ランキング | 自身の知見を業界に還元、見えない貢献者から見える存在へ |
| JA 普及員 | 組合員提案時のエビデンス確保、コミュニティ知見の参照 | 普及員の経験知が組織を超えて流通 |
| 研究者 | 現場データへのアクセス、研究シードの発見 | 研究知見の社会実装、産業との接続 |
| メーカー | 市場フィードバックの直接取得、ランキング掲載による露出 | 信頼性ある情報チャネル、口コミ獲得 |

### 1.4 KPI 候補

> 🔥 ローンチ後 1-2 ヶ月の評価軸を 3 名で合意したい。

| 指標 | 目的 | 仮目標（ローンチ + 1 ヶ月） |
|---|---|---|
| 登録ユーザー数（ロール別） | 各ロールへのリーチ | farmer 100 / maker 10 / 他 5 |
| アクティブレビュー投稿者数 | 「貢献する」側のエンゲージメント | farmer 20 名以上 |
| 資材登録数 | メーカー側の供給 | 30 製品以上 |
| 1 製品あたり平均レビュー数 | コンテンツ密度 | 3 件以上 |
| 資材詳細ページ閲覧 / レビュー投稿率 | コンバージョン | 5% 以上 |
| Farmille AI クエリ回数（DAU） | AI 機能の実用性検証 | 20 query/day |
| メーカー公開ページ閲覧数 | メーカー流入導線 | 累計 500 PV |

## 2. 設計哲学

技術判断の前提（`.claude/skills/farmille-architecture-principles/SKILL.md` 要約）。

| 原則 | 内容 | ビジネスへの含意 |
|---|---|---|
| DOA 優先 | データモデルは技術負債を作らない。UI は後から作り直せるが DB は不可逆 | データ事業化の選択肢を残す |
| ポータビリティ予算 | Supabase / Railway / Vercel の独自機能依存は「引っ越せる範囲」 | 値上げ / 障害時の switching cost を低く保つ |
| 責務分離 | ビジネスロジックは全て FastAPI を経由。フロント直接 DB は認証・写真の 2 例外のみ | セキュリティ第一防御を BFF に集約 |
| 二重防御 | FastAPI で認可（第一防御）、DB 側 RLS で第二防御 | BFF バグや直接アクセスへの保険 |
| v1 スコープ厳守 | やらないことリストを作業中に動かさない | 7 月ローンチ死守 |

> 📌 本 PRD では §6「v1 やらない」リストを **MVP 反映後に更新**。Farmille AI は v1 入りに変更（旧版は v2.5 候補だった）。

## 3. ロール定義

| ロール | 内部キー | 登録方法 | 主な権限 | 想定母数（v1） |
|---|---|---|---|---|
| 農家 | `farmer` | サインアップで自己選択 | 資材閲覧、レビュー投稿/編集/削除、写真アップロード、コミュニティ閲覧 + 投稿（要決定） | 100 名 |
| JA 普及員 | `ja_staff` | 管理者割当（v1 はサインアップ不可） | 農家と同等のレビュー権限 | 5 名 |
| 研究者 | `researcher` | 管理者割当（v1 はサインアップ不可） | 農家と同等のレビュー権限 | 5 名 |
| メーカー | `maker` | サインアップで自己選択（v1 は誰でも登録可） | 自社資材の登録/編集/削除、画像管理、メーカー公開プロフィール編集 | 10 社 |
| 未確定 | `unassigned` | サインアップ直後 | プロフィール設定のみ | （遷移状態） |
| 未ログイン | （なし） | – | 資材一覧・詳細・メーカー一覧・ランキング・コミュニティ閲覧、Farmille AI（制限あり、要設計） | （流入のメイン） |

**二層構造**:
- ロールは Supabase Auth の `app_metadata.role`（JWT 由来、改ざん不可）と `public.users.role`（DB 列、SQL 集計用）の両方に保持
- 書き込みは必ず `POST /v1/auth/register-role` 経由で原子的に両方更新
- 詳細: `docs/decisions/0002-reviews-insert-role-scope.md`

## 6. v1 で意図的にやらないこと（更新）

> ⚠️ 旧版から **AI 構造化を除外**（v1 入りに変更、§4.6 参照）。

| 項目 | 理由 | 検討再開の条件 |
|---|---|---|
| モバイルアプリ（iOS / Android） | 開発リソース、PWA で代替可 | MAU 一定規模、モバイル流入が PC を超えたら |
| マッチング機能 | 業務フロー設計が大物、両側動機検証が先 | 両側ユーザー均衡、自然発生的要望 |
| プッシュ通知・リアルタイム更新 | エンゲージメントツールは流入確保後 | 月次 retention 立ち上がり |
| 管理者画面 | 暫定は SQL 直アクセスで代替 | 手動運用の限界 |
| インセンティブ設計（割引・ランク・バッジ） | ピュアな価値検証を優先 | 自然発生的貢献量の頭打ち |
| 農協との正式連携 | パイロット選定 / 契約スキーム要 | パイロット JA 合意 |
| Google 以外の OAuth | ターゲット層は Google 利用率高 | 特定セグメント要望 |
| PWA 化 | モバイル体験は v1.5+ で検討 | モバイル流入増加 |

> 🔄 **コミュニティ機能**は biz 議論次第で v1 入り可能性あり（`biz-discussion-agenda.md` §A）。決定次第このセクションから移動 / 残置を確定する。

## 9. 長期ビジョン

> 🔥 Ryoga 加筆余地あり。3 名で議論して書き換えてください。

### 9.1 5 年後の世界観

**「BS 資材に関する意思決定は、まず Farmille を見る」状態。**

- 日本の主要 BS 資材メーカーがほぼ全て登録（数百社）
- 月次 MAU 数万（農家の 5-10% が定期利用）
- レビュー数 数万件、AI 構造化済みデータベース
- JA 共販の選定参考データの 1 つに採用
- 学術論文・農研機構レポートでデータが引用される

### 9.2 事業化の 3 つの方向性

| 方向性 | 概要 | 課金主体 | リスク |
|---|---|---|---|
| メーカー向け SaaS | 分析ダッシュボード、競合比較、レビュー通知 | メーカー | データ偏重で農家離れ、メーカー忖度疑念 |
| データ事業 | レビューデータの集計を JA / 商社 / 研究機関に提供 | B2B | 個人情報の取り扱い、農家側同意設計 |
| マッチング / 取引 | サンプル配布、購買仲介、共同購入 | 取引手数料 | 物流・規制・信頼の三重コスト |

### 9.3 業界エコシステムでの位置取り

```
[農家] ←─レビュー─→ [Farmille] ←─マスタ・分析─→ [メーカー]
                        ↑
                        └─ [JA / 普及員 / 研究者] ←─ 知見提供
```

- 「中立的な情報インフラ」のポジションを死守する
- メーカー課金が始まっても、農家側の体験は無料・広告なしを維持
- データ事業に出る場合も、個人特定不可な集計のみ

### 9.4 「やらない」長期方針（v3+ でも）

- BS 資材以外への横展開（農薬一般、種苗、農機具）→ ブランド希薄化リスク
- 自社製品販売 → メーカー中立性の毀損
- ソーシャル機能（タイムライン、フォロー、いいね）→ レビュー品質低下リスク

### 10.1 性能

| 指標 | 現状 | 目標 |
|---|---|---|
| ランディング first paint | <500ms | <300ms |
| `/products` first paint | 1-3 秒（streaming 改修前） | 200ms（Phase 14 完了後） |
| `/products/[id]` first paint | 1-2 秒 | 500ms |
| API レスポンス | 100-500ms | <300ms |
| Farmille AI 応答 | – | <3 秒（ストリーミング含む） |

### 10.2 可用性

| 項目 | 現状 |
|---|---|
| フロント | Vercel（無料枠、SLA なし） |
| バックエンド | Railway Hobby（$5/月、SLA なし） |
| DB | Supabase Free（500MB、無料枠） |
| 想定可用性 | 99% 程度 |

### 10.3 セキュリティ

| 項目 | 内容 |
|---|---|
| 認証 | Supabase Auth（JWT、メール認証必須） |
| 認可 | BFF（FastAPI）第一防御、Postgres RLS 第二防御 |
| ロール改ざん防止 | `app_metadata.role`（service_role 権限のみ書込） |
| 写真アップロード | Storage RLS でパス強制 |
| 監査 | Sentry、Railway / Vercel ログ |
| AI 入出力 | プロンプトインジェクション対策、PII フィルタ要設計 |

### 10.4 保守性

| 項目 | 内容 |
|---|---|
| マイグレーション | Supabase migrations（番号管理） |
| 型生成 | `pnpm gen:types` で TS 型を Supabase スキーマから自動生成 |
| ADR | `docs/decisions/` |
| Spec | `docs/specs/` |

### 10.5 ポータビリティ

| 項目 | 内容 |
|---|---|
| Railway 依存 | `RAILWAY_*` 直参照禁止、`API_URL` 等の汎用名でラップ |
| Supabase 依存 | Edge Functions / Vault 不採用、PostgreSQL 機能のみ |
| LLM プロバイダ依存 | 採用判断時に ADR で switching cost を明記 |
| Dockerfile | multi-stage、他 PaaS でも動作可能 |
