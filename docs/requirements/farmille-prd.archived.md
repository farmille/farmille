## 1. プロダクト概要

### 1.1 ミッション

**BS資材（生物・微生物農業資材）の現場使用感を、現場の言葉で集めて構造化する。**

農薬・化成肥料の代替として注目される BS 資材は、効果の出方が圃場・作目・気候で大きく変わるため、メーカー公表のスペックだけでは導入判断が難しい。Farmille は実使用者（農家・JA 普及員・研究者）のレビューを集積し、メーカー・購入検討者の双方が**業務判断に使えるレビュープラットフォーム**を目指す。

### 1.2 ターゲットユーザー

| セグメント | 役割 | Farmille での行動 |
|---|---|---|
| 農家 | BS 資材の購入検討 / 利用者 | 資材検索、レビュー閲覧、レビュー投稿 |
| JA 普及員 | 組合員への資材推奨 | レビュー閲覧、現場知見の投稿（v2 で JA ダッシュボード想定） |
| 研究者（大学・農研機構等） | 資材効果の学術的検証 | レビュー閲覧、専門的視点での投稿 |
| メーカー | 自社資材の認知獲得・市場フィードバック | 自社資材登録、レビュー監視（v2 で分析機能） |

### 1.3 提供価値（4 ロール × 2 軸）

| ロール | 「探す」価値 | 「貢献する」価値 |
|---|---|---|
| 農家 | 圃場条件に近い実例レビューを横断検索 | 自身の知見を業界に還元、見えない貢献者から見える存在へ |
| JA 普及員 | 組合員提案時のエビデンス確保 | 普及員の経験知が組織を超えて流通 |
| 研究者 | 現場データへのアクセス、研究シードの発見 | 研究知見の社会実装、産業との接続 |
| メーカー | 市場フィードバックの直接取得 | 信頼性ある情報チャネル、口コミ獲得 |

### 1.4 KPI 候補（v1 ローンチ後の検証指標、要合意）

> 🔥 **要議論**: ローンチ後 1-2 ヶ月の評価軸を 3 名で合意したい。

| 指標 | 目的 | 仮目標（v1 ローンチ + 1 ヶ月） |
|---|---|---|
| 登録ユーザー数（ロール別） | 各ロールへのリーチ | farmer 100 / maker 10 / 他 5 |
| アクティブレビュー投稿者数 | 「貢献する」側のエンゲージメント | farmer 20 名以上 |
| 資材登録数 | メーカー側の供給 | 30 製品以上 |
| 1 製品あたり平均レビュー数 | コンテンツ密度 | 3 件以上 |
| 資材詳細ページ閲覧 / レビュー投稿率 | コンバージョン | 5% 以上 |

## 2. 設計哲学

技術判断の前提にしている思想（`.claude/skills/farmille-architecture-principles/SKILL.md` の要約）。

| 原則 | 内容 | ビジネスへの含意 |
|---|---|---|
| DOA 優先（Data-Oriented Architecture） | データモデルは技術負債を作らない。UI は後からいくらでも作り直せるが DB は不可逆。正規化・制約・スケーラビリティを妥協しない | 「ピボットしてもデータが活きる」状態を維持。データ事業化（§9）の選択肢を残す |
| ポータビリティ予算 | Supabase / Railway / Vercel の独自機能依存は「引っ越せる範囲」に留める | 値上げ / 障害 / 戦略変更時の switching cost を低く保つ |
| 責務分離（Next.js / FastAPI / Supabase） | ビジネスロジックは全て FastAPI を経由。フロント直接 DB アクセスは認証・写真アップロードの 2 例外のみ | セキュリティ第一防御を BFF に集約、ロジック分散による事故を防ぐ |
| 二重防御 | FastAPI で認可（第一防御）、DB 側 RLS で第二防御 | BFF バグや直接アクセスへの保険、セキュリティ監査が通りやすい |
| v1 スコープ厳守 | やらないことリストを作業中に動かさない。良さそうに見える機能追加でも v1 は却下 | 7 月ローンチを死守、機能膨張による遅延を防ぐ |

## 3. ロール定義

| ロール | 内部キー | 登録方法 | 主な権限 | 想定母数（v1） |
|---|---|---|---|---|
| 農家 | `farmer` | サインアップで自己選択 | 資材閲覧、レビュー投稿/編集/削除、写真アップロード | 100 名 |
| JA 普及員 | `ja_staff` | バックエンド管理者割当（v1 はサインアップ不可） | 農家と同等のレビュー権限（将来 JA 用ダッシュボード） | 5 名 |
| 研究者 | `researcher` | バックエンド管理者割当（v1 はサインアップ不可） | 農家と同等のレビュー権限 | 5 名 |
| メーカー | `maker` | サインアップで自己選択（v1 は誰でも登録可） | 自社資材の登録/編集/削除、画像管理 | 10 社 |
| 未確定 | `unassigned` | サインアップ直後の初期状態 | プロフィール設定のみ。各機能はオンボーディング誘導でブロック | （遷移状態） |
| 未ログイン | （なし） | – | 資材一覧・詳細の閲覧のみ。レビュー投稿等は `/login` 誘導 | （流入のメイン） |

**二層構造の補足**（技術詳細）:
- ロールは Supabase Auth の `app_metadata.role`（JWT 由来、改ざん不可）と `public.users.role`（DB 列、SQL 集計用）の両方に保持
- 書き込みは必ず `POST /v1/auth/register-role` 経由で原子的に両方更新
- 詳細: `docs/decisions/0002-reviewer-role-unification.md`

## 6. v1 で意図的にやらないこと（確定）

> ⚠️ **認識ずれがないか 3 名で確認**。動かすときは別途 ADR を起票する。

| 項目 | 理由 | 検討再開の条件 |
|---|---|---|
| AI によるレビュー構造化・推薦 | 7 月ローンチ優先、価値検証が先 | レビュー数が一定規模に達し、構造化の ROI が見込めたら |
| モバイルアプリ（iOS / Android） | 開発リソース、PWA で代替可 | MAU が一定規模、モバイル流入が PC を超えたら |
| マッチング機能（メーカー↔農家のサンプル申請） | 業務フロー設計が大物、両側の動機検証が先 | 両側ユーザー数が均衡し、自然発生的なつながり要望が出てきたら |
| プッシュ通知・リアルタイム更新 | エンゲージメントツールは流入確保後 | 月次 retention が立ち上がってから |
| 管理者画面（モデレーション、統計、運用） | 暫定は SQL 直アクセスで代替 | レビュー数 / メーカー登録数が手動で追えなくなる規模 |
| インセンティブ設計（割引・ランク） | 複雑化要因、ピュアな価値検証を優先 | 自然発生的な貢献量が頭打ちになったら |
| 農協との正式連携 | パイロット先選定 / 契約スキームが必要 | パイロット JA との合意が取れたら |
| Google 以外の OAuth | ターゲット層は Google 利用率高 | 特定セグメントから要望が出たら |
| PWA 化 | モバイル体験は v1.5+ で検討 | モバイル流入が増えたら |

## 7. 保留中の業務判断（要 ビズ合意）

> 🔥 **このセクションが本ドキュメントの核**。3 名で順に決めていく。

| # | 論点 | 影響範囲 | 仮案（Ryoga） | 議論ポイント | 緊急度 |

| 2 | **メーカーアカウントの承認フロー** | 登録ハードル、信頼性、運用負荷 | v1 は誰でも登録可、v1.5 で軽い審査追加（企業情報手動確認） | 偽メーカー登録のリスク vs オープンさ、運用工数 | 中 |
| 3 | **事前登録済みユーザーの引き継ぎフロー** | β ユーザー / 事前登録名簿の取り込み方 | – | そもそも引き継ぐべき名簿がどれだけあるか、認証どう紐付けるか | 中（ローンチ前に決定推奨） |
| 4 | **JA 普及員 / 研究者のサインアップ経路** | v1 は管理者割当のみ、自己登録不可 | v1.5 で組織コード入力による自己登録方式、または運用フォーム経由 | 偽研究者問題、組織との信頼関係構築 | 中 |
| 5 | **メーカーレビュー監視・通知** | メーカー側エンゲージメント、UX | v1 は自社資材一覧のみ、v1.5 で「自社資材へのレビュー通知」追加 | メール通知 vs アプリ内、頻度設計 | 低 |
| 6 | **レビュー削除時の「履歴を残すか」** | 監査性、法的対応、メーカーの信頼 | hard delete（CASCADE）で運用、削除証跡は別途監査ログで | soft delete に移行する判断軸、復元要望 | 低 |
| 7 | **コンテンツモデレーション方針** | 不適切投稿への対応、運用体制 | v1 は人手対応（運営問い合わせ）、v1.5 で報告ボタン + 簡易管理画面 | 報告閾値、削除権限、メーカーからの異議申立 | 中 |
| 8 | **ローンチ告知 / PR 戦略** | β ユーザー獲得経路 | – | JA / 農学会 / Twitter / メーカーへの直接営業のどれを優先 | 高（ローンチ前） |

## 8. v2 候補機能（要 ビズ合意 = 本ドキュメントの主目的）

> 🔥 **本ドキュメントの最重要セクション**。`.claude/skills/farmille-architecture-principles/SKILL.md` §1.4 の「v1 やらない」を全て候補として並べた。
>
> 各候補について **採用 / 延期 / 不採用** を 3 名で取捨選択する。採用するなら優先順位（P0/P1/P2）と工数感の概算をつける。

### 8.1 AI によるレビュー構造化・推薦

| 観点 | 内容 |
|---|---|
| ビジネス価値 | レビューの質的な集約が可能に。「肥料の代わりに使った例」「収量改善した例」などの軸で串刺し検索ができる。メーカーへの提供価値が大きく上がる |
| 想定ユーザー | 農家（探す）、メーカー（インサイト取得）、研究者（学術活用） |
| 概要 | レビュー本文を LLM で構造化（効果・条件・圃場特性）、類似レビュー推薦、製品レコメンド |
| 技術的難易度 | 中〜高（LLM API コスト、構造化スキーマ設計、評価指標） |
| 依存・前提 | レビュー数が最低 500 件以上（学習・評価のため） |
| 議論ポイント | LLM API コスト負担、構造化スキーマの粒度、ハルシネーション許容度、メーカー利用は有料か |

## 9. 長期ビジョン

> 🔥 **要 Ryoga 加筆**。ここは私（Claude）の解釈ベース。Ryoga が実際の構想を持っているはずなので、3 名で議論して書き換えてください。

### 9.1 5 年後の世界観（Ryoga 仮説）

**「BS 資材に関する意思決定は、まず Farmille を見る」状態。**

- 日本の主要 BS 資材メーカーがほぼ全て登録（数百社）
- 月次 MAU 数万（農家の 5-10% が定期利用）
- レビュー数 数万件、AI 構造化済みデータベース
- JA 共販の選定参考データの 1 つに採用
- 学術論文・農研機構レポートでデータが引用される

### 9.2 事業化の 3 つの方向性（議論用）

| 方向性 | 概要 | 課金主体 | リスク |
|---|---|---|---|
| **メーカー向け SaaS** | 分析ダッシュボード、競合比較、レビュー通知 | メーカー | データ偏重で農家離れ、メーカー忖度疑念 |
| **データ事業** | レビューデータの集計・分析を JA / 商社 / 研究機関に提供 | B2B | 個人情報の取り扱い、農家側の同意設計 |
| **マッチング / 取引** | サンプル配布、購買仲介、共同購入 | 取引手数料 | 物流・規制・信頼の三重コスト |

### 9.3 業界エコシステムでの位置取り

```
[農家] ←─レビュー─→ [Farmille] ←─マスタ・分析─→ [メーカー]
                        ↑
                        └─ [JA / 普及員 / 研究者] ←─ 知見提供
```

- 「中立的な情報インフラ」のポジションを死守する
- メーカー課金が始まっても、農家側の体験は無料・広告なしを維持
- データ事業に出る場合も、個人特定不可な集計のみ

### 9.4 「やらない」長期方針（v3+ でも）

- BS 資材以外への横展開（農薬一般、種苗、農機具）→ ブランドの希薄化リスク
- 自社製品販売 → メーカー中立性の毀損
- ソーシャル機能（タイムライン、フォロー、いいね）→ レビュー品質の低下リスク

> 上記 §9 の全項目は **Ryoga の仮説**。共同創業者間で実際にどこまで合意できているか、すり合わせが必要。

|---|---|

| DB | Supabase Free（500MB、無料枠） |
| 想定可用性 | 99% 程度（無料枠依存、定期メンテ吸収可能） |

### 10.3 セキュリティ

| 項目 | 内容 |
|---|---|
| 認証 | Supabase Auth（JWT、メール認証必須） |
| 認可 | BFF（FastAPI）で第一防御、Postgres RLS で第二防御 |
| ロール改ざん防止 | `app_metadata.role`（service_role 権限でのみ書き込み可） |
| 写真アップロード | Storage RLS でパス強制 (`{user_id}/{review_id}/`) |
| 監査 | Sentry（エラー追跡）、Railway / Vercel ログ |

詳細: `docs/decisions/0005-jwt-verification-strategy.md`, `0007-storage-rls-audit.md`

### 10.4 保守性

| 項目 | 内容 |
|---|---|
| マイグレーション | Supabase migrations（番号管理） |
| 型生成 | `pnpm gen:types` で TS 型を Supabase スキーマから自動生成 |
| ADR | `docs/decisions/` に主要技術判断を記録 |
| Spec | `docs/specs/` に各 phase の実装仕様を保管 |

### 10.5 ポータビリティ

| 項目 | 内容 |
|---|---|
| Railway 依存 | `RAILWAY_*` 環境変数を直接参照しない（`API_URL` 等の汎用名にラップ） |
| Supabase 依存 | Edge Functions / Vault は不採用、PostgreSQL 機能のみ使用 |
| Dockerfile | multi-stage、他 PaaS でも動作可能 |
