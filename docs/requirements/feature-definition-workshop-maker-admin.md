## 0. このドキュメントの使い方

### 0.1 各論点の読み方

各トピックは以下の 11 項目テンプレートで構成されています（既存 `feature-definition-workshop.md` と完全同一の構造）。

```
0) 機能サマリ          1-2 文での要約
1) MVP 観測 / 現状      確認できた事実（Claude / researcher 記入済み）
2) ユーザーとゴール     誰が、何のために
3) ユーザーストーリー   "〜として、〜したい、なぜなら〜"
4) 画面要素             画面と主要 UI 要素
5) 主要データ項目       テーブル / フィールドの粗い形

8) Claude 案（叩き）    推奨と理由
9) 事前コメント欄       奥田さん / 根本さん記入
10) 会議での決定        やる/やらない、期限、担当
```

1. **事前段階（1 週間程度）**

## M1. メーカー拡張ダッシュボード `/maker` ⚠️

### M1.0 機能サマリ
既存 `/maker/products` を拡張し、メーカーが自社運用を一元管理できる専用ハブ画面 `/maker` を構築する。

### M1.1 MVP 観測 / 現状
- 本リポ実装: `/maker/products`（自社製品の一覧 + 登録 + 編集）のみ
- MVP も同等。メーカー専用ダッシュボードは MVP / 本リポ双方で未実装
- researcher 調査:
  - **食べログ owner**: 9 機能カテゴリ（検索設定 / 店舗ページ編集 / ネット予約 / Tポイント / レポート / 口コミ / 店舗会員情報 / プラン / 各種サービス）の左メニュー型ハブ
  - **Yelp for Business**: 無料機能（ページ更新 / メッセージ応答 / レビュー返信 / リード追跡 / 閲覧数）+ 有料広告
  - **Amazon Seller Central**: 7 一級メニュー、ブランド代表者ロール必須
  - **AgList**: 本格メーカー機能は後追いで段階追加
- SKILL §1.4 「未確定」: 「メーカー側ダッシュボード（`/maker/products` 拡張）」次回定例議題

### M1.2 ユーザーとゴール
- **メーカー**: ログイン後にダッシュボードで自社の状況（製品数 / 新着レビュー / お悩み相談スレ / 使用版希望リスト）を一画面で把握する
- **メーカー**: 自社運用に必要な操作を画面遷移最小で行う
- **運営**: メーカー継続率を上げる（一覧画面だけだと再訪動機が弱い）

### M1.3 ユーザーストーリー
- メーカーとして、ログイン直後に「自社製品数 / 直近 7 日の新着レビュー数 / 未回答のお悩み相談スレ数 / 未対応の使用版希望者数」を 1 画面で見たい。複数タブを開かなくて済むから。
- メーカーとして、ダッシュボードから「自社プロフ編集」「商品登録」「レビュー一覧」「相談室応答」「使用版希望者リスト」へワンクリックで遷移したい。
- メーカーとして、自社プロフィール（メーカー公開ページ §3.3）の閲覧数や直近の問い合わせ件数を把握したい（アクセス分析の v1 採否は要決定）。

### M1.4 画面要素
- `/maker` トップ — カード型ナビ（食べログ owner の左メニュー構造を参考）
  - **自社プロフィール**カード: 公開ページへのリンク + 編集ボタン
  - **商品**カード: 自社製品数 + 「商品を登録」ボタン（既存 `/maker/products` へ遷移）
  - **レビュー**カード: 直近 7 日の新着件数 + 平均★評価 + 「一覧を見る」（M2 連動）
  - **お悩み相談**カード: 未回答スレ数 + 「相談室を見る」（M3 連動）
  - **使用版希望**カード: 未対応件数 + 「リストを見る」（M4 連動）
  - **アクセス分析**カード（v1 採否要決定）: 自社公開ページの閲覧数推移
- ヘッダー: アバター + ロール表示（maker）+ ログアウト

### M1.5 主要データ項目
既存テーブル（`maker_profiles` / `products` / `reviews`）を集約クエリで参照。**新規テーブルは想定しない**。
- 製品数: `SELECT COUNT(*) FROM products WHERE maker_id = $1`
- 新着レビュー: `SELECT COUNT(*) FROM reviews JOIN products ... WHERE created_at > now() - interval '7 days'`
- 未回答スレ・未対応希望者: M3 / M4 のテーブル設計確定後

### M1.6 ロール権限
- 閲覧 / 操作: 自社のみ（`maker_id = auth.uid()`）
- BFF: `GET /v1/maker/dashboard` のような集約エンドポイント、`require_role("maker")` で保護

### M1.7 v1 スコープ外
- 競合メーカー比較
- CSV エクスポート（一覧の生データ出力）
- 有料広告枠購入 UI（Yelp Ads 相当、v1 は不採用、v1.5+ 議論）
- プラン分岐 UI（無料 / 有料）
- 多店舗メーカーの統合管理（Amazon Seller Central のブランド階層）

### M1.8 Claude 案（叩き）
**推奨: v1 はカード型ナビ + 最小集計（製品数 / 新着レビュー件数 / 未回答スレ数 / 未対応希望者数）のみ。各カードの詳細機能（M2〜M4）は議論結果次第で順次追加。**

理由:
- AgList も本格メーカー機能を段階的に足した経緯あり、初期は薄くて十分
- 集計クエリのみで新規テーブル不要 → DOA レビューが軽い
- アクセス分析は §P アナリティクスとの整合が要るので v1 採否は会議で確定

## M2. レビュー集計・通知 ⚠️

### M2.0 機能サマリ
自社製品レビューの集計表示 + 新着レビューのメール通知。Yelp for Business と食べログ owner の口コミ機能を参考とする。

### M2.1 MVP 観測 / 現状
- 本リポ / MVP 双方で未実装
- 既存 `reviews` テーブル + RLS で「自社製品のレビュー閲覧」自体は可能、集計 UI とメール通知が未着手
- researcher 調査:
  - **食べログ owner**: 口コミの自由文返信 + ピックアップ口コミ（運営選定）
  - **Yelp for Business**: レビュー返信は無料機能、新着リード追跡あり
  - **Amazon Seller Central**: レビュー応答は **テンプレ 2 択固定**（自由文不可、規制が厳しすぎ Farmille には不向き）
- 既存 workshop §5（メーカー向けレビュー監視・通知）で v1.5 推奨案あり

### M2.2 ユーザーとゴール
- **メーカー**: 自社製品の★評価分布 / レビュー件数 / 直近トレンドを 1 画面で把握する
- **メーカー**: 新着レビューを見逃さず、低評価レビューに早期対応する
- **運営**: メーカーがレビュー対応に動くことで、レビュー文化を健全に保つ

### M2.3 ユーザーストーリー
- メーカーとして、自社製品ごとの★評価分布（1-5 各件数）と平均★を一覧で見たい。改善優先順位を決めたいから。
- メーカーとして、自社製品に新着レビューが付いたらメールで知りたい。毎日ログインするわけではないから。
- メーカーとして、低評価レビュー（★1-2）にだけ絞り込んで一覧したい。対応漏れを防ぎたいから。

### M2.4 画面要素
- `/maker/reviews`（URL 仮）
  - 上部: 自社全体の集計（総レビュー件数 / 平均★ / 各★件数の棒グラフ）
  - フィルタ: 製品 / 評価 / 期間
  - 一覧: レビューカード（製品名 / ★ / 投稿日 / 投稿者表示名 / 本文抜粋 / 詳細リンク）
  - **メーカーから農家への返信機能の有無は要決定**（公平性 / メーカー有利化リスク）
- メール通知: 新着レビュー発生時、自社メーカー連絡先メールへ即時通知（テンプレ + 該当レビューへの直リンク）

### M2.5 主要データ項目
- 既存 `reviews` / `products` を集約クエリで参照
- メール通知は v1 では **全員強制 ON**（メーカーが受信先メールを設定済みなら通知）。ON/OFF 切替の業務要件は v1.5+ で議論
- メーカー → 農家への返信機能の v1 採否は M2.10 で決定。採用時のテーブル設計は spec 起草時に DOA レビューで確定（本書では新規テーブルを提案しない）

### M2.6 ロール権限
- 自社レビュー閲覧: maker（自社製品のみ、`maker_id = auth.uid()` で制約）
- 集計 API: BFF の `/v1/maker/reviews/*`、`require_role("maker")` で保護
- メーカー返信機能の権限粒度は v1 採否確定後

### M2.7 v1 スコープ外
- 自動 AI 要約（既存 §1.4 やらない、データ蓄積待ち）
- メーカー側のレビュー削除リクエストフォーム（運営手動対応で代替）
- 有料の上位表示（Yelp Ads 相当）
- 競合製品比較
- CSV エクスポート

### M2.8 Claude 案（叩き）
**推奨: v1 は「集計表示（自社全体 + 製品別）+ メール通知」のみ。メーカーから農家への返信機能は v1.5+ で議論。**

理由:
- 食べログ owner はレビュー自由文返信を実装しているが、Farmille は初期レビュー数が少なく公平性懸念が大きい（メーカー側が低評価レビューに「営業反応」しすぎると農家投稿が萎縮）
- Amazon の **テンプレ 2 択固定**は安全寄りだが UI が貧弱。v1 はそもそも返信不可で逃げる方が無難
- 集計 + 通知だけなら新規テーブル最小（あっても通知 ON/OFF 1 つ）、DOA 負荷低い

## M3. お悩み相談室 応答ワークフロー（メーカー側ビュー）⚠️

### M3.0 機能サマリ
`farmille-v1-functional-requirements.md` §3.3 で定義したお悩み相談室を、メーカー側がどう運用するかの専用画面・業務フロー。

### M3.1 MVP 観測 / 現状
- 本リポ / MVP 双方でお悩み相談室自体が未実装
- 機能要件 md §3.3 で「企業ページに併設、AgList にない差別化要素」として位置づけ
- researcher 調査:
  - **食べログ owner**: 口コミ返信機能はあるがスレッド形式ではない
  - **Yelp for Business**: メッセージ応答機能あり、リード追跡と一体
  - **Reddit Mod Tools**: AutoModerator が毎日の投稿の 82% を自動処理（Farmille 初期は不要、参考程度）

### M3.2 ユーザーとゴール
- **メーカー**: 自社宛のお悩み相談スレッドを一覧 / 未回答数を把握 / 過去応答履歴を辿る
- **メーカー**: 農家との対話で信頼を築き、サンプル提供や購入動機につなげる
- **農家**: メーカーから誠実な応答を受け、業務判断のエビデンスを得る

### M3.3 ユーザーストーリー
- メーカーとして、`/maker/threads`（仮）で自社宛の質問スレッド一覧を見たい。新着順 / 未回答順で並べたい。
- メーカーとして、各スレッドに自由文で返信したい。テンプレートでは農家の細かい状況に応えられないから。
- メーカーとして、過去の自社応答履歴を検索したい。同じ質問が来た時に過去応答を流用したい。
- メーカーとして、応答が任意か必須かを明確に把握したい（強制応答は炎上リスク）。

### M3.4 画面要素
- `/maker/threads`（URL 仮）
  - 上部: 未回答スレ件数 / 平均応答時間（v1 採否要決定）
  - フィルタ: 製品別 / ステータス（未回答 / 回答済 / 自社クローズ）
  - 一覧: スレッドカード（タイトル / 投稿者表示名 / 投稿日 / 直近返信日 / 返信数 / 詳細リンク）
- スレッド詳細: 機能要件 md §3.3.4 の `/manufacturers/{slug}/threads/{id}` をメーカー側からも閲覧可
  - メーカー側返信フォーム（自由文）
  - 「クローズする」ボタン（自社判断、農家には別文言で表示）

### M3.5 主要データ項目
- 機能要件 md §3.3.5 の `manufacturer_threads` / `manufacturer_thread_replies` を参照（所有節は §3.3）
- メーカー側ビューは集約クエリのみ、新規テーブルなし想定

### M3.6 ロール権限
- 自社宛スレッド閲覧: maker（自社のみ）
- スレッド返信: maker（自社スレッドのみ、`require_role("maker")` + 自社制約）
- スレッドクローズ: maker（自社のみ）+ 運営（モデレーション）
- スレッド作成権限（誰が起票できるか）は機能要件 md §5.2.1 §5.2.2 で要決定

### M3.7 v1 スコープ外
- 自動応答 bot（AI / テンプレ提案）
- 応答テンプレ集（業界 FAQ）
- スレッドのリアルタイム通知（v1 はメール + 再読込）
- 応答 SLA 監視（運営側ダッシュボード、v1.5+）
- 複数担当者による分担応答（v1 はメーカーアカウント 1 つ前提）

### M3.8 Claude 案（叩き）
**推奨: v1 は「任意応答（強制応答なし）」+ 「自由文返信」+ 「メール通知（M2 と統合）」のみ。応答必須化や SLA 監視は v1.5+。**

理由:
- 強制応答化すると、メーカーが対応リソース足りずに放置 → スレッドが大量未回答で炎上、というリスクが大きい
- v1 はメーカー数少ない（30 社想定）ため、未回答が積み上がる前に運営が個別声がけで耐える
- テンプレ集や bot は誤応答リスクあり、レビュー文化が育つまで保留
