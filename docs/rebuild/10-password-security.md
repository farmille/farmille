# アカウントのパスワード管理

## 対象と操作

一般・メーカー・運営の既存アカウントを対象とする。パスワードはアカウントの非公開属性であり、新しい業務オブジェクトや一覧を作らない。認証と設定は補助画面として扱う。

- ログイン中の利用者は、自分のアカウントから現在のパスワードを照合して変更する。
- ログインできない利用者は、ログイン画面から再設定メールを要求する。
- メーカーの認証用内部メールと連絡先メールは分離したままにし、配送時に承認済みアカウントの連絡先へ解決する。

## 画面と経路

一般のマイページ、メーカーのダッシュボード、運営ホームから共通の `/account/password` を開く。運営の変更にはAAL2を要求する。変更後はセッションを終了し、アカウント種別に対応したログイン画面へ案内する。

一般・運営は `/password-reset`、メーカーは `/sellers/password-reset` からメールを要求する。メーカーはログインIDと登録済みの連絡先メールを入力する。登録の有無・不一致・承認状態を送信結果から判別できない文言にする。

再設定メールは `/password-reset/update` へ誘導する。入力画面を開くだけではトークンを消費せず、新しいパスワードの送信時にSupabaseのrecoveryトークンを検証する。通常のログインセッションだけでは再設定できない。再設定後はログインをやり直す。MFAの登録は削除しない。

2要素認証を設定したアカウントは、認証アプリのコードも入力する。メール検証後のセッションは、再設定専用の署名付きHttpOnly cookieで10分間保持する。コードの入力をやり直してもメールを再送する必要はない。cookieは元のメールリンクに結び付け、通常ログインのセッションを再設定の証明として受け付けない。変更後はこのcookieとSupabaseのセッションを失効させる。

## 配送と境界

SupabaseのSend Email HookをNext.jsの外部向けRoute Handlerで受け、署名を検証してからメールを配送する。メーカーの送信先は署名済みのAuthユーザーIDからDBで解決し、フォームやユーザー編集可能なmetadataを送信先の根拠にしない。再設定のトークン発行、失効、送信頻度の制限はSupabase Authに委ねる。

本番はResendのSMTPを利用する。ローカルはメール検証用SMTPで受信する。配送エラーは成功として扱わず、トークン・パスワード・メール本文をログへ出さない。

ローカルでは `pnpm dev` とE2Eの両方でポート3007を使用する。Supabaseのメールフックは `http://host.docker.internal:3007/api/auth/email` を呼び出すため、メール送信時にはアプリを起動しておく。既存の `.env.local` でも `NEXT_PUBLIC_SITE_URL=http://127.0.0.1:3007` を指定し、`.env.example` のSMTP関連3変数を設定する。メールは `http://127.0.0.1:54324` で確認できる。

## 検証条件

3種別の変更と再設定、新旧パスワードでのログイン、現在パスワードの誤り、確認欄の不一致、期限切れ・使用済み・不正トークン、メーカーの宛先解決と未承認状態、MFAの維持を確認する。SP375pxとPC1280pxの画面を撮影し、画面遷移図へ追加する。本番の配送設定と実際の受信が確認できるまで完了としない。
