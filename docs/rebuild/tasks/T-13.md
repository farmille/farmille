# T-13 認証基盤（一般／メーカー／admin AAL2・認証4画面）

あなたは認証・認可の実装に厳密なフルスタックエンジニアです。仕様の正は `docs/rebuild/01-domain-model.md` §4（認証設計）・§5（RLS の前提）と `docs/rebuild/02-screens.md` §2（認証画面）。UI はデザイントークン（panda.config.ts・semanticTokens）経由で、モック（docs/rebuild/reference/mockup-sp-19screens.html の signup 画面）と同じデザイン言語にする。

## 制約

- 触ってよいのは `src/`（app の認証系ルート・server/auth 系・proxy.ts・middleware 相当）・`.env.example`
- `src/server/supabase.ts`・`result.ts`・`errors.ts`（T-14 成果）を必ず使う。重複実装しない
- 合成メールのドメインは `sellers.farmille.internal` 固定（01 §4）。クライアントに合成メールを露出しない
- パスワード・トークンをログに出さない

## 実装範囲

1. **一般ユーザー登録 `/signup/general`**：ハンドルネーム・メール・パスワード・立場の4項目。立場は農家／JA関係者／専門家・研究者／その他から1件を必須選択し、内部属性としてだけ保持する。アイコンは登録後にマイページで設定できる旨を表示する。送信で Supabase signUp ＋ `profiles` 行作成（server action。app_metadata.account_type='general' の付与は admin クライアントで）。完了画面→ホームへ
2. **一般ログイン `/login`・パスワード再設定 `/password-reset`**：Supabase 標準フロー。`?next=` は既存の `safeNextPath` で検証
3. **メーカーログイン `/sellers/login`**：ログイン ID＋パスワード入力 → server action で `seller_accounts.login_id` を引き approved を確認 → 合成メールで signInWithPassword。失敗時は ID/パスワードのどちらが誤りか判別できない文言
4. **セッションユーティリティ `src/server/auth.ts`**：`getSessionUser()`（memoize）・`getAccountType()`・`requireGeneralUser()`・`requireSeller()`（seller_id 返却）・`requireAdmin()`（**account_type='admin' かつ AAL2。AAL 不足は `aal2_required`**）
5. **proxy.ts（Next 16 の middleware 相当）**：Supabase セッション cookie 更新＋保護パス（`/me`・`/post`・`/dashboard`・`/admin` は要ログイン、`/login`・`/signup` はログイン済みならリダイレクト）。公開ページ（D6）は素通し
6. admin の MFA enroll/challenge 画面は**このタスクでは作らない**（admin UI は T-44。ここは requireAdmin の判定だけ）

## 検証（完了条件）

```bash
pnpm lint && pnpm format:check && pnpm exec tsc --noEmit && pnpm exec vitest run && pnpm build
```

ローカル Supabase スタック（`npx supabase start`）を起動して実フロー確認：
- signup → profiles 行が作られ handle 重複が弾かれる
- login/logout、`/me` への未ログインアクセスが `/login` へ、`?next=` の細工 URL（`/\t/evil.example` 等）が `/` に落ちる
- メーカー：seed で仮 seller（approved・login_id）を1件作り、ID ログインが通る・未承認 ID は拒否される
- 上記の実行ログ（curl か Playwright の簡易スクリプトで可）を報告に貼る

safe-next 相当のユニットテストに加え、`auth.ts` の判定ロジック（account_type・AAL 分岐）はモック JWT でユニットテスト化する。

## 質問すべき条件

- profiles 作成と auth ユーザー作成の整合（片方失敗時の巻き戻し）で 01 に無い設計判断が必要になったら、採った方式を必ず報告に明記（DB トリガー方式 vs server action 内の補償処理）
- スキーマ・RLS が仕様どおり動かない場合は server 側で回避せず停止して報告

## 最終報告の形式

実装ファイル一覧／検証結果（コマンド＋実フロー確認ログ）／設計判断（profiles 作成方式・セッション更新方式）／未実装として残した点。
