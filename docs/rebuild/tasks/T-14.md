# T-14 src/server 基盤（Supabase クライアント・エラー契約・共通クエリ）

あなたは Next.js のサーバーサイド設計に長けたエンジニアです。以後の全機能タスクが乗る `src/server/` の土台を作る。規約の正は `docs/rebuild/03-architecture.md` §2・§8。

## 制約

- 触ってよいのは `src/server/`・`src/lib/`（追加のみ）・`src/types/`（読み取り）・`src/env.ts`（必要な拡張のみ）
- 画面（src/app/）は触らない
- `any` 禁止。すべて `src/types/database.types.ts` から型を導出
- silent fallback 禁止

## 手順

1. `src/server/supabase.ts`：
   - `createServerSupabase()`（@supabase/ssr・cookie 連携・anon キー。Server Components / Route Handlers / Server Actions で共用）
   - `createAdminSupabase()`（service_role。**この関数はこのファイル外に露出する型を supabase クライアントに限定**し、env.ts のサーバー専用検証を通す。使用箇所を grep しやすいよう命名固定）
2. `src/server/result.ts`：`Result<T> = { ok: true; data: T } | { ok: false; error: ErrorCode }`。`fail(code)`・`succeed(data)`。HTTP 応答化ヘルパ `toResponse(result, status?)`（D9 の `{ok:false, error}` 形式）
3. `src/server/errors.ts`：ErrorCode の union（最低限：`unauthorized`・`forbidden`・`not_found`・`invalid_body`・`conflict`・`aal2_required`・`internal`。機能タスクが追加していく前提のコメント）と、コード→日本語文言辞書 `errorMessageJa`
4. `src/server/Pagination.ts`：`pageRange(page, perPage)` と `Paginated<T>` 型
5. 手本となる共通クエリ2本（以後のタスクの参照実装）：
   - `src/server/queries/materials.ts`：`listMaterials({ filters?, page })`（公開・集計カラム込み・効果／作物／製品タイプ／検索補助タグは同一分類 OR・分類間 AND）と `getMaterial(id)`（画像・エビデンス・正規化分類込み）
   - `src/server/queries/reviews.ts`：`listReviewsByMaterial(materialId, { sort, page })`（published のみ・投稿者の公開プロフィール join）
   - いずれも戻り値は database.types 由来の型から `Pick`/変換した明示的な DTO 型。**分類検索の AND/OR 仕様は docs/rebuild/02-screens.md §2 の検索欄と 01 §3 を参照**
6. ユニットテスト：result.ts・pagination.ts・errors.ts の純粋ロジック（vitest）。クエリはローカル Supabase が起動していれば統合テスト1本（起動していなければ skip 判定にして CI を壊さない）
7. 検証・コミット

## 検証（完了条件）

```bash
pnpm lint && pnpm format:check && pnpm exec tsc --noEmit && pnpm exec vitest run && pnpm build
```

## 質問すべき条件
