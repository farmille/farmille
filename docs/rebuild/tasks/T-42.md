# T-42 メーカーダッシュボード（自社資材・資材変更申請）

あなたは権限境界に厳密なフルスタックエンジニアです。対象：`/dashboard`・`/dashboard/materials/[id]`。仕様は `01-domain-model.md` §3 materials（2層構造・カラム単位保護トリガーあり）・`02-screens.md` §2。モックに無い画面のため、キット部品＋資材詳細ページの視覚言語で構成する（単独スクリーンショットで可）。

## 定型制約（04 §3・必須）

- 共通 UI キットで組む。不足部品はキット追加が先。ページ側 styled-system 直接使用はレイアウト調整のみ

## その他の制約

- 触ってよいのは `src/app/dashboard/`（新規。articles 配下は T-43 の領域なので**作らない**）・`src/server/`（seller 系追加）・components/ への追加
- requireSeller() で保護。**編集できるのは一次情報層のみ**（description・general_use・main_components・mechanism・usage_text・price_range・official_url・catalog_url）。分類・検索層（name・manufacturer_name・sales_status・組成タイプ・効果・対象作物・材料・製品タイプ・検索補助タグ）は閲覧のみ＋「分類変更を申請」
- server 層は admin クライアントではなく**ユーザーセッションのクライアント**で更新し、RLS・保護トリガーを実効させる（第二防御の実地検証を兼ねる）

## 実装

1. **`/dashboard`**：メーカー情報カード（public_sellers 相当＋内部項目は自分のみ）・claim 済み資材一覧（0件時は「資材の掲載を希望する場合は運営にご連絡ください」）・記事管理への導線（/dashboard/articles。T-43 未実装でも 404 でよい）・ログアウト
2. **`/dashboard/materials/[id]`**：自社資材のみアクセス可（他社は notFound）。全情報とエビデンスの変更、初期データの確認、掲載終了を対象付近から操作する。メーカーによる変更は `material_change_requests` と提案子テーブルへ保存し、運営承認後だけ正本へ反映する。自分の申請履歴と状態も表示する
3. 保存成功・失敗の文言はエラー辞書経由。分類層カラムを触ろうとした場合の保護トリガー発火をエラー表示で吸収

## 検証（完了条件）

ゲート一式（pipefail）＋実フロー（ローカル：approved seller のシードは T-13 検証手順を再利用）：自社資材の紹介文更新→公開側 /materials/[id] に反映。他社資材 URL 直叩き→notFound。分類層の直接更新が DB 層で拒否されること（保護トリガーの実効確認）。エビデンス追加→公開側に表示。申請 INSERT。375px スクリーンショット。

## 質問すべき条件

- 一次情報層のカラム構成が 01 と database.types で食い違ったら停止して報告

## 最終報告の形式

実装ファイル一覧／検証結果（RLS・トリガー実効の証跡含む）／キット追加の有無／設計判断。
