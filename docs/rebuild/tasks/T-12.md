# T-12 資材マスタの v2 移行パイプライン（旧 seed SQL → 新スキーマ）

> **改訂（2026-07-26・調査結果反映）**：旧 seed SQL に含まれる資材は **15件のみ**（294 という数字は INSERT 文の総数で製品数ではない）。フル資材マスタ（381製品/84社）は本番 DB と gitignore 済み Excel にしか存在せず、リモートアクセス（T-06）まで取得不能。**本タスクの目標を「変換パイプラインの完成＋15件でのローカル開発シード」に変更する。**件数照合は「ソースから抽出できた実数」との一致で判定し、294 は完了条件から除外。パイプラインは入力（旧形式の INSERT SQL または CSV/JSON ダンプ）を差し替えればフルデータでも動く構造にし、フル投入の手順を README の TODO に明記すること。

あなたはデータ移行を正確に行うエンジニアです。リモート DB へのアクセスは無い前提で、**リポジトリ内に残っている旧 seed SQL をデータソース**として v2 スキーマ向けの投入 SQL を生成する。

## 制約

- 触ってよいのは `tools/migration/` 配下のみ（`legacy/` は読み取り専用）
- リモート DB（--linked）接続禁止。検証はローカルスタック（`npx supabase start` 済み環境）のみ
- v2 スキーマ（`supabase/migrations/`）は読み取り専用。変更が必要だと思ったら止まって報告
- 数値・文言の捏造禁止。元データに無い値は NULL のままにする

## 入力（データソース）

- `tools/migration/legacy/migrations-v1/20260526000003_seed_products_from_ryosei_export.sql`（約327KB。products 294件・product_images・product_application_recipes の INSERT。maker は `maker_profiles.company_name = '…'` のサブクエリで解決している——**この company_name 文字列が v2 の `materials.manufacturer_name` になる**）
- `tools/migration/legacy/migrations-v1/20260415000002_farmille_seedgenre.sql`（product_types 等の旧マスタ）
- 旧スキーマ定義：同ディレクトリの `20260415000000_farmille_init.sql`・`20260526000000/2_admin_aglist_v2_*.sql`
- v2 スキーマ：`supabase/migrations/`（T-11 の成果）と `docs/rebuild/01-domain-model.md` §3・§8

## 手順

1. 旧 seed SQL をパースし、中間データ（JSON）に正規化する変換スクリプトを `tools/migration/` に作成（Node スクリプト。`node` 単体で動くこと。依存を増やさない）
2. v2 向け投入 SQL `tools/migration/materials-v2-seed.sql` を生成：
   - `materials`：name・manufacturer_name（company_name 文字列）・一次情報層は旧 products の対応カラム（general_use・ingredients 等、旧カラム名との対応表を報告に含める）・`seller_id = NULL`（全件未 claim）
   - `material_images`：URL・image_type・sort_order を引き継ぐ
   - `materials.usage_text`：product_application_recipes を「作物／目的／使い方」の読める箇条書きテキストに整形して集約（01 §8）
   - 旧 products の product_type → v2 の `materials.product_type` と `material_tags`（type 分類タグ）への対応。タグは T-11 のシード（tags テーブル）に存在するもののみ紐づけ、対応が無いものは報告に列挙
   - `material_sources` は**今回投入しない**（データがリポジトリに無い。リモートアクセス取得後の追補として tools/migration/README.md に明記）
   - 冪等性：`ON CONFLICT` か事前 DELETE で再実行可能にする
3. ローカルスタックに適用して検証：materials=294件・画像件数が旧と一致・無作為5件のフィールド突合（旧 INSERT 文と目視比較できる形で出力）
4. `tools/migration/README.md` を新規作成：実行手順（ローカル／将来のリモート）・データ来歴・source 追補の TODO
5. コミット

## 検証（完了条件）

- ローカルへの適用ログと件数照合の出力（294／画像件数／5件突合）
- 再実行（冪等性）してもエラー・重複が出ないこと

## 質問すべき条件

- 旧→新のカラム対応が 01 から一意に決まらないフィールドが出たら、対応表の該当行に「要確認」と付けて**投入は NULL** にし、報告で列挙する（勝手にそれらしい値を入れない）

## 最終報告の形式

旧→新カラム対応表／件数照合結果／タグ対応の欠落一覧／要確認フィールド一覧。
