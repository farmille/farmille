## 1. コンテキスト

2026-05-06 定例で biz から「**講演会がメインのマネタイズ**になる」「集客・連絡できる機能を v1 に入れる」「メーカーが講演会モードで一斉メール送信できるようにしたい」という発言があった。

既存方針との衝突:

- **SKILL §1.4 やらない表**「イベント機能（メーカー主催勉強会・千人規模通知）— メーカーリレーション構築が先」と衝突
- **機能要件 §4**「v1.5+ で再検討」と衝突
- **PRD §9.3**「メーカー有料化 v1 アウト」と部分衝突（講演会機能の有料化は別途、v1 ローンチ時は全機能無料）

worker session（2026-05-13）で実装側解像度を詰めた結果:

- 講演会主体: v1 はメーカー主催のみ + アドミン手動の運営主催あり
- 開催形式: v1 は告知ページ + 申込フォームだけ、開催形式（オンライン / オフライン / 録画）はメーカー本文自由記入
- メール一斉送信: メーカーがセグメント（自社製品をマイ資材に保管中の農家 / 個別ユーザー指定 等）を選択可能
- メーカーフォロー機能は **暗黙フォロー**（既存 `user_favorites` から `DISTINCT manufacturer_id` で導出）、新規テーブル不要

## 2. 決定

### 2.1 講演会機能の v1 完版採用

機能要件 §3.8 で L3 起草済み。要点:

- 新規 URL: `/events`（一覧）+ `/events/{id}`（詳細）
- 新規テーブル `events` / `event_registrations`
- メーカー側 CRUD: `/maker/events`（§3.7 メーカーダッシュボード）
- アドミン側手動運営主催: `/admin/events/new`（§3.9 B7 拡張）
- メール一斉送信: `/maker/emails`（§3.7）

### 2.2 メーカーフォロー = 暗黙フォロー

- 新規テーブル `user_maker_follows` を作らない
- 既存 `user_favorites` テーブルから集計クエリで導出: `SELECT DISTINCT manufacturer_id FROM user_favorites WHERE user_id = $1`
- メーカー側から見たフォロワー集合: `SELECT user_id FROM user_favorites WHERE manufacturer_id IN (自社製品の maker_id) GROUP BY user_id`
- v1.5+ で明示フォロー UI / `user_maker_follows` テーブル新設を検討（§5.4.8）

### 2.3 メーカー一斉メールのセグメント

`maker_email_campaigns.segment_type` enum（spec 起草時 DOA レビュー）:

- `favorite_followers`: 自社製品をお気に入り / 候補に追加した農家
- `event_past_attendees`: 過去の講演会申込者
- `specific_users`: 個別ユーザー指定（運営仲介で限定運用）

法規制対応:

- 一斉メール送信は特商法 / 電気通信事業法に抵触しないよう、**規約条項**に「メーカーからの案内メールを受け取ること」の同意項目を追加（§5.1.2 §5.2.23）
- 「個別ユーザー指定」は v1 では運営仲介で限定運用、無差別送信を防ぐ

### 2.4 v1 スコープ外（v1.5+ 延期）

- Farmille 内決済（参加費徴収）→ メーカーが本文に外部決済リンクを記載 or 当日現金
- 録画ホスティング → メーカーが YouTube / Vimeo リンクを本文に貼る
- 自動リマインダーメール
- 申込キャンセル UI（v1 は spec 起草時に最低限を判断）
- 申込上限超過時のキャンセル待ち管理
- カレンダー連携（iCal / Google Calendar）
- 講演会後アンケート / フィードバック収集
- 本文構造化（開催形式 / 参加費 / 録画提供有無のスキーマ化）

## 3. 採用した代替案

### A. v1 アウト維持 + v1.5+ 延期（却下）
- biz が「メインのマネタイズ」と発言しているのを v1.5+ に延期すると、ローンチ後のマネタイズ動線が空白になる
- 「使用版」CTA 撤回でメーカー × 農家接点が減ったため、講演会が代替接点として必須

### B. 講演会 = 告知ページのみ + 申込は外部フォーム（却下）
- メーカー視点で「自社メーラーに切り替える」操作が増える
- Farmille で申込データを持たないと、メーカーフォロワーとのリンクが取れない

### C. 講演会 + 申込フォーム + メール一斉 を全部 v1（採用）
- biz「v1 完版採用」発言と整合
- 申込データを Farmille で持つことで、暗黙フォロワー集合計算 + 一斉メールセグメントが成立
- 開催形式 / 参加費 / 録画は本文自由記入で「軽い構造化」とし、データモデルは最小

### D. メーカーフォロー = 明示テーブル（却下、暗黙フォローを採用）
- 新規テーブル `user_maker_follows` を作ると DOA レビュー対象が増える
- 既存 `user_favorites` で暗黙フォローが成立するので、追加スキーマは不要
- v1.5+ で明示フォローが必要になったらテーブル新設可（§5.4.8）

## 4. 帰結

### Positive
- メーカーマネタイズ動線が v1 ローンチ時に揃う
- 暗黙フォローで新規テーブル不要、DOA レビュー軽い
- 開催形式の構造化を保留することで、v1 スコープを最小に保てる

### Negative
- スコープ拡大（新規 2 テーブル + 新規 URL 群）
- 一斉メール送信の法規制対応で規約条項追加が必須
- 「個別ユーザー指定」セグメントの運用ルール（無差別送信防止）を運営側で定義する必要
- メーカーが本文を雑に書くと、ユーザー体験がメーカー間で揃わない（v1.5+ で構造化検討）

### 中立
- v1 ローンチ時は全機能無料 → メーカー有料化フェーズ（2026-06+）で講演会機能を有料プランの目玉にする選択肢

## 5. 移行手順

1. migration: `events` / `event_registrations` / `maker_email_campaigns` テーブル作成 + RLS ポリシー
2. backend: `/v1/events/*` / `/v1/maker/events/*` / `/v1/admin/events/*` / `/v1/maker/emails/*` エンドポイント追加
3. frontend: `/events` / `/events/{id}` / `/maker/events` / `/maker/emails` / `/admin/events/new` ルーティング
4. 規約条項追加（§5.1.2 §5.2.23）
5. メーカーへの機能告知メール（運営手動）
